# Bussy — очередь задач для ИИ-агента

> Этот файл — источник задач. `AGENTS.md` перезаписывается `next dev`,
> поэтому задачи живут здесь. Формулировка запроса агенту:
> «сделай задачу N из TASKS.md».

## Как работать

Иди строго по порядку. Одна задача — один прогон — одна остановка на ревью.
Не бери следующую, пока предыдущая не принята.

Перед завершением любой задачи запусти и убедись, что чисто:

```bash
npx tsc --noEmit
npm run lint
npm test
```

Если задача трогала маршруты, стриминг или сборку — дополнительно `npm run build`.
«Скомпилировалось» не равно «работает».

## Блок A — надёжность демо

### Задача 1 — чат ломается после длинного ответа (критично)

**Файл:** `lib/ai/chat-config.ts`, строки 27–37.

`ChatMessageSchema` проверяет `content.max(MAX_MESSAGE_CHARS)` до того, как
вызывается `trimConversation`. Клиент (`app/app/chat/page.tsx`) отправляет всю
историю обратно с каждым запросом, поэтому один ответ ассистента длиннее
4 000 символов приводит к 400 на всех последующих запросах, пока пользователь
не перезагрузит страницу. Со стримингом ответы длиннее, и вероятность выше.

**Должно стать:** слишком длинное сообщение обрезается, а не отклоняется.
Статус 400 остаётся только для действительно невалидного тела: не тот `role`,
пустой `content`, не JSON. То же для поля `userMessage`.

**Проверка:** тест в `lib/ai/conversation.test.ts` — история, где одно
сообщение ассистента длиной 10 000 символов, даёт 200, а не 400.

### Задача 2 — стриминг и время выполнения

**Файл:** `app/api/chat/route.ts`.

1. В заголовки SSE-ответа добавь `"X-Accel-Buffering": "no"`. Без него
   буферизующий прокси накапливает поток и отдаёт все шаги разом в конце —
   прогресс агента пропадает на продакшене.
2. Добавь `export const maxDuration = 60` и снизь `OPENAI_TIMEOUT_MS` до
   `15_000`. Цикл агента делает до `MAX_AGENT_STEPS` вызовов OpenAI, и на
   serverless функцию убьют посреди ответа.

Примечание: route handler принимает только экспорты HTTP-методов, НО
`maxDuration`, `runtime` и `dynamic` — штатный route segment config, их
экспортировать можно.

**Проверка:** `npm run build` проходит; стрим по-прежнему отдаёт события по
мере готовности.

## Блок B — неверные числа на экране

### Задача 3 — недостижимая безубыточность показывается как «0»

**Файлы:** `app/app/finance/page.tsx`, `app/app/simulator/page.tsx`,
`lib/i18n/translations.ts`.

`calculateBreakEven` при `sellingPrice <= variableCostPerUnit` возвращает
`breakEvenUnits: 0`, и страницы печатают «0 ta». Пользователь читает это как
«окупаешься с нуля продаж», хотя безубыточность недостижима в принципе.

**НЕ меняй типы в `lib/engine/breakeven.ts`** — у `BreakEvenResult` много
потребителей, смена на `number | null` сейчас слишком рискованна. Исправь на
уровне отображения: если `contributionMargin === 0 && breakEvenUnits === 0`,
вместо числа выведи строку из переводов о том, что при такой цене
безубыточность недостижима и нужно поднять цену или снизить себестоимость.

`fixedCost === 0` — другой случай, там безубыточность достигается сразу.
Не схлопывай два условия в одну ветку.

**Проверка:** на странице finance при цене ниже себестоимости показывается
объяснение, а не «0». Обе локали.

### Задача 4 — нулевой бизнес показан здоровым

**Файл:** `lib/engine/cashflow.ts`.

При `revenue = 0` и `expenses = 0` получается `netCashflow = 0` и статус
`healthy` с текстом про устойчивый положительный поток.

**Должно стать:** при `revenue === 0` статус не может быть `healthy`.
Добавь ветку и текст в обе локали.

**Проверка:** тест в `lib/engine/engine.test.ts` на нулевую выручку.

## Блок C — доверие к цифрам

Жюри задало прямой вопрос: «как вы считаете кредит и налоги». Задачи этого
блока отвечают на него прямо в интерфейсе.

### Задача 5 — кнопка «Показать формулу» (высокий приоритет)

**Файлы:** `components/chat/calculation-card.tsx`, страницы loan и finance,
`lib/i18n/translations.ts`.

Сейчас пользователь видит только результат. Нет способа проверить, откуда
взялось число, — а это главный вопрос к финансовому продукту.

**Должно стать:** рядом с каждым рассчитанным значением — сворачиваемый блок
«Formulani ko'rsatish» / «Show formula». Внутри: сама формула и подставленные
значения. Пример для кредита:

```
M = P × (r(1+r)ⁿ) / ((1+r)ⁿ − 1)
P = 50 000 000    r = 24% / 12 = 0,02    n = 24
M = 2 643 555 so'm
```

Минимум: кредит (аннуитет), точка безубыточности, чистая прибыль, налог по
выбранному режиму.

**Важно:** формулы и подставленные значения берутся из уже посчитанного
результата движка, а НЕ считаются заново в компоненте. Если для отображения
не хватает промежуточных значений — добавь их в результат функции движка,
не дублируй вычисление.

**Проверка:** значение в блоке формулы совпадает с отображаемым результатом на
всех проверенных примерах. Тест на то, что промежуточные значения возвращаются
движком.

### Задача 6 — правовое основание налоговых ставок

**Файлы:** новый `lib/engine/tax-sources.ts`, `lib/engine/tax.ts`,
`app/app/tax/page.tsx`.

Ставки в `tax.ts` захардкожены без указания источника и даты. Пользователь и
проверяющий не могут убедиться, что они актуальны.

**Должно стать:** отдельный модуль со ссылкой на норму и датой актуальности
для каждой ставки, и вывод этой строки под ставкой в интерфейсе. Структура:

```ts
export interface TaxSource {
  rateId: string;        // "turnover" | "profit" | "vat" | ...
  legalBasis: string;    // ссылка на норму — ЗАПОЛНЯЕТ ЧЕЛОВЕК
  effectiveFrom: string; // ISO-дата
  verifiedBy?: string;   // кто проверил
}
```

**КРИТИЧНО: не придумывай номера статей Налогового кодекса.** Оставь
`legalBasis` пустой строкой с комментарием `// TODO: заполнить после проверки
бухгалтером`. Ошибочная ссылка на закон хуже её отсутствия. Если `legalBasis`
пустой — интерфейс показывает «ставка на проверке», а не выдуманный источник.

**Проверка:** страница налогов показывает дату актуальности под каждой ставкой;
пустой `legalBasis` не ломает вёрстку.

### Задача 7 — льготная ставка налога с оборота 1%

**Файлы:** `lib/engine/tax.ts`, `app/app/tax/page.tsx`, переводы.

Для самозанятых и плательщиков с оборотом до 1 млрд сум действует льготная
ставка 1%, а в интерфейсе доступна только стандартная 4%. В `assumptions`
про льготы упомянуто, но выбрать их нельзя.

**Должно стать:** в режиме `turnover` можно выбрать ставку — 4% по умолчанию
или 1% льготная, с пояснением, кому она положена. Поле `customRate` в
`calculateTax` уже существует, используй его, сигнатуру не меняй.

**Проверка:** тест на расчёт по ставке 1%; переключение видно в обеих локалях.

### Задача 8 — допущения видны на всех страницах с расчётами

**Файлы:** `app/app/finance/page.tsx`, `app/app/simulator/page.tsx`,
`app/app/business-plan/page.tsx`.

Массивы `assumptions` уже выводятся на страницах loan и tax, но на finance,
simulator и business-plan допущения (разделение расходов 60/40, 30 дней в
месяце, средний чек по типу бизнеса) не показаны, хотя влияют на результат.

**Должно стать:** на каждой странице с расчётом — блок «Hisob-kitob
taxminlari» в том же стиле, что уже есть на странице loan. Тексты из
`lib/engine/assumptions.ts` и переводов, не инлайном.

## Блок D — необязательное

### Задача 9 — лишние токены в результате инструмента

**Файл:** `lib/ai/run-tool.ts`.

`calculateLoan` возвращает полный график амортизации на 24–60 строк, и весь он
уходит модели как результат инструмента — 800–2 000 токенов впустую на каждый
вызов.

**Должно стать:** модель получает только итоги — `monthlyPayment`,
`totalPayment`, `totalInterest`. Полный объект с графиком по-прежнему попадает
в `steps[]`, чтобы UI рисовал таблицу и график.

**Не меняй сигнатуру `calculateLoan`.** Движок остаётся как есть, фильтрация
на границе с моделью.

### Задача 10 — сообщения об ошибках только на узбекском

**Файл:** `app/api/chat/route.ts`.

`locale` уже разбирается из тела запроса, 429 переведён, а ответы 400 и 500 —
нет. Англоязычный пользователь при сбое получит узбекский текст.

**Должно стать:** все ответы с ошибкой уважают `locale`, тексты — в
`lib/i18n/translations.ts`, не инлайном.
